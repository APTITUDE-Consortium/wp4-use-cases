### 5.3 Current Constraints, Limitations and Pain Points

**Pain points (hospitality / UC 10):**

- Identity matching by string comparison → high error rate, manual reconciliation.
- Fragmented mobile key ecosystems — each hotel chain has its own app.
- Regulatory heterogeneity — every Member State has its own guest registration API and required attribute set.
- No portable booking confirmation — each booking re-issued separately, not reusable.
- Manual transcription of foreign IDs at reception.
- Long check-in queues at peak times.
- Privacy over-disclosure — full passport copy taken even when only name + DOB needed.

**Constraints UC 10 must work within:**

| Constraint | Implication for UC 10 |
| --- | --- |
| Door locks are typically offline | Room Key EAA must support offline verification (cached issuer key) |
| Hotel networks may be unreliable in rooms / corridors | Wallet must operate offline; cached credentials required |
| Door lock hardware diversity | Room Key EAA payload must be vendor-agnostic; integration layer at hotel side |
| National registration APIs are not interoperable | Phase 5 VP must be transformable to country-specific API formats |
| Limited EUDIW market penetration in 2026 | Manual fallback (UP1, UP2) must remain available |
| Door reader battery / processing constraints | Verification must be lightweight (no heavy crypto, no online TIL lookup) |
| Hotel staff training | UI/UX of fallback flows must be near-identical to today's process |

**Next steps:** Door lock vendor's specific technical limits (e.g., NFC payload size, BLE protocol support).
