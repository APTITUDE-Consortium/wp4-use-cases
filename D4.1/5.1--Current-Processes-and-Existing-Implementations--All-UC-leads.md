### 5.1 Current Processes and Existing Implementations (Hospitality / UC 10 contribution)

**Content to draft (hospitality sector baseline):**

**Today's hotel booking & check-in process:**

1. **Booking** — User books via OTA (Booking.com, Expedia) or hotel website; identity is unverified at booking, only payment is verified.
2. **Pre-arrival** — Email confirmation with booking reference; some chains offer mobile check-in (proprietary apps).
3. **Check-in** — Physical ID document (passport, national ID) presented at reception; clerk visually verifies and copies/scans.
4. **Guest registration** — Hotel transmits guest data to police/local registry via national APIs (e.g., SES.Hospedajes in Spain, AlloggiatiWeb in Italy, Meldeschein in Germany) — per-country fragmented APIs.
5. **Room access** — Physical key card (Mifare/RFID) programmed at reception; some chains use proprietary mobile keys (Hilton Honors, Marriott Bonvoy) — non-portable across chains.
6. **Checkout** — Manual or app-based.

**Existing digital infrastructure UC 10 must interoperate with:**

| System | Function | Interoperability point |
| --- | --- | --- |
| Property Management System (PMS) — Opera, Mews, Apaleo, Protel | Booking, room assignment, billing | Booking EAA + Room Key EAA issuance triggered by PMS events |
| Door lock systems — Assa Abloy, Salto, Dormakaba, Onity | Physical room access | Room Key EAA must produce a credential the lock can validate (NFC/BLE protocol) |
| Channel managers / OTAs | Distribution | Out of scope for pilot but data flows through them |
| National guest registration APIs (SES.Hospedajes, AlloggiatiWeb, Meldeschein) | Regulatory reporting | Phase 5 VP must produce data fields these APIs require |
| Hotel CRM / loyalty | Guest preferences | Out of scope for pilot |
