### 5.2 Identity Matching and Management (Hospitality / UC 10 contribution)

**Today's approach (hospitality):**

- **Booking:** name string entered manually — no identity verification.
- **Check-in:** clerk visually compares physical ID name with booking name string.
- **Failure modes:**
  - Transliteration (e.g., "Müller" vs "Mueller", Cyrillic↔Latin)
  - Title/middle-name handling (booking has "John Smith", passport says "John Robert Smith")
  - Married vs maiden name mismatches
  - OTA-truncated or auto-transformed names
- **No portable identity across chains** (each chain re-verifies).
- **No cross-border identity layer** (foreign passports manually transcribed → typos).

**How EUDIW solves these in UC 10:**

- PID is cryptographically bound to the holder (no possibility of impersonation).
- Booking is created from the PID itself (Phase 2) → name on booking == name on PID by construction → eliminates transliteration mismatches.
- Check-in becomes cryptographic verification, not visual comparison.
- Same EUDIW + PID works across any hotel/chain in any Member State (portability).
- Authority reporting (Phase 5) sources data directly from the PID → no manual transcription errors.
